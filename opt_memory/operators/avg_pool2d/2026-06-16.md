## Iter 1: tilelang-design-nhwc-vectorized

- **改动**：TileLang block_level + tile_level 设计：NCHW→NHWC layout 转换，block_M=128 沿 spatial 分块，T.copy 向量化加载 4 个 2×2 窗口行到 UB，T.tile.add 累加 + T.tile.mul ×0.25 求平均，每个输出 row (C 个通道) 独立处理
- **性能**：0.0 TFLOPS，利用率 0.0%
- **状态**：✅通过
- **洞察**：NHWC layout 使同一空间位置的 C 个通道在内存中连续，可利用 T.copy 向量化加载和 T.tile.* 向量化计算，避免标量逐元素 GetValue/SetValue。设计阶段无性能数据，进入 AscendC 转译后获取实测

## Iter 2: ascendc-translation-nhwc-vectorized

- **改动**：转译 TileLang NHWC 设计到 AscendC：TQue depth=1 管理 UB 缓冲区，DataCopyPad GM↔UB 向量化搬运 4 个窗口行（每行 C 个 float32），Add 累加 + Muls ×0.25 求平均。S1/S3 精度通过，S2 有 0.345% 微小偏差
- **性能**：0.0 TFLOPS，利用率 0.0%
- **状态**：⚠️部分改善
- **洞察**：NHWC + DataCopyPad 向量化方案基本正确，S1(64ch)/S3(512ch) 通过，S2(256ch) 有微小偏差可能来自 DataCopyPadParams 对齐或边界条件。先进入性能评估再看是否需要修复

## Iter 3: performance-baseline-nhwc-v1

- **改动**：性能基线: NHWC + DataCopy + TQue 向量化实现，PyTorch 0.277ms vs AscendC 0.397ms (0.70x 加速，即更慢)。Shape 极小(max 401K 输出)，launch overhead+permute 主导
- **性能**：0.005 TFLOPS，利用率 0.0015%
- **状态**：⚠️部分改善
- **洞察**：Shape 极小导致 launch overhead 主导。需要：(1) 减少 per-position TQue 开销，批量处理多个输出位置；(2) 减少 permute 开销，考虑在 kernel 内处理 NCHW layout 或融合 layout 转换

## Iter 4: final-verified-nhwc-tque

- **改动**：全 3 shape 精度通过。性能: PyTorch 0.314ms vs AscendC 0.398ms (0.79x)。NHWC + DataCopy + TQue 向量化方案正确但受 launch+permute overhead 限制
- **性能**：0.005 TFLOPS，利用率 0.0015%
- **状态**：✅通过
- **洞察**：avg_pool2d shape 极小，launch/permute overhead 主导 (~300us)。NHWC 向量化方案功能正确，优化空间在于融合 layout 转换或批量处理。shape 更大的 pooling 场景下此方案应有明显收益
